# Telegram MCP

Самостоятельный сервер с 12 MCP-инструментами для чтения переписки, поиска
получателей и управляемой отправки. Работает без AI Kit и mcp-platform.
Python 3.12–3.14; FastMCP 4.0.0 закреплён вместе с зависимостями в `uv.lock`.
В 0.2.0 добавлены настройщик и проверки неполного поиска получателя.

```sh
uv sync --frozen --all-groups
uv run python scripts/verify.py
uv build
```

Пакет содержит настоящий upstream Telegram MCP в приватном namespace и
сохранённый патч платформы. Источник: chigwell/telegram-mcp, tag `v3.2.0`,
commit `f1a2d8e00a7f127bb7702655c58fdfcee7e73a5a` (его metadata version — `2.0.1`).
Это сторонний Apache-2.0 upstream, а обёртка, публичные инструменты и standalone
политика — отдельные части проекта. `SOURCE_PROVENANCE.json`, `vendor/` и
`src/zai_telegram/_vendor/manifest.json` фиксируют происхождение, патч и хеши.
Загрузка не использует одноимённый пакет из PyPI; проверяет упакованные файлы.

Для запуска оператор создаёт приватный env-файл с `TELEGRAM_API_ID`,
`TELEGRAM_API_HASH` и `TELEGRAM_SESSION_STRING` либо сессиями
`TELEGRAM_SESSION_STRING_<LABEL>`. Локальный настройщик может создать сессию интерактивно; вход не является MCP-инструментом. Реальные значения не помещаются в репозиторий.

Отдельный приватный JSON задаёт серверную привязку пользователей:

```json
{"local-operator": "default", "alice": "work"}
```

Установить `TELEGRAM_SECRET_FILE` и `TELEGRAM_BINDINGS_FILE` в абсолютные пути
этих файлов; `TELEGRAM_STATE_PATH` — постоянная приватная SQLite-база. На POSIX
файлы принадлежат оператору/root и имеют mode 0600; на Windows доступ
обеспечивается ACL учётной записи службы. Пример переменных — `.env.example`;
сервер читает переменные процесса, а не автоматически найденный `.env`.

```sh
zai-telegram-mcp --transport stdio
zai-telegram-mcp --transport http --host 127.0.0.1 --port 8816
```

stdio использует `TELEGRAM_LOCAL_PRINCIPAL` и `TELEGRAM_LOCAL_SCOPES`
(по умолчанию `local-operator`, `telegram:read`). Для HTTP обязательны
`TELEGRAM_MCP_PUBLIC_KEY_FILE` (RSA public PEM), JWT RS256 от своего issuer с
audience, сроком exp, sub и `account_id`, совпадающим с `TELEGRAM_ACCOUNT_ID`.
Scopes — `telegram:read`, `telegram:write`. Путь — `/mcp`.
Account label берётся только из серверного JSON; JWT/аргумент клиента не меняет
привязку. Для записи дополнительно нужен `TELEGRAM_WRITE_ENABLED=true`.

Лимиты по умолчанию на одну метку аккаунта: 30 вызовов upstream MCP/минуту, включая до 20
записей и до 3 операций высокого риска; до 2 одновременно. Настройки могут
уменьшать эти значения. Это учёт операций MCP; внутренние MTProto запросы и
повторы Telethon остаются частью закреплённого upstream. SQLite хранит квоты, cooldown, аудит метаданных и
журнал отправок между перезапусками. Один общий путь state обязателен для
процессов с одинаковыми аккаунтами; независимые базы не координируют квоты.
Список допустимых upstream-операций записи закреплён в адаптере.

Повтор успешного idempotency key возвращает сохранённый результат. Изменение
его payload/account отклоняется. При неопределённом результате отправки запись
остаётся `pending`; повтор и новый ключ для того же pending-запроса не отправляют
сообщение повторно. Перед дальнейшей отправкой оператор сверяет результат
в Telegram. Автоматического снятия pending или повторной отправки нет.
`telegram_send_many` выполняет до 20 элементов последовательно с отдельными
результатами; это не атомарная рассылка. `telegram_outbox_status` показывает
журнал текущего пользователя. Доказанный локальный отказ квоты до отправки
получает `failed`: после освобождения лимита можно использовать новый ключ.
Сохраняйте базу вместе с рабочими аккаунтами.

Upstream содержит состояние клиентов на уровне процесса. Один процесс
использует один неизменяемый набор sessions/режима записи; смена требует
перезапуска. Сессии, proxy, файловый log и roots fallback из постороннего
окружения не подхватываются; принимаются только разрешённые ключи env-файла.

Платформа может подключить закреплённый wheel и зарегистрировать те же tools,
передав свои registry/settings/store. Тогда авторизация, квоты, аудит и
журнал принадлежат платформе; standalone SQLite не запускается. Внешние
контракты сохранены в `src/zai_telegram/_contracts/telegram.json`.

Проверки используют синтетические fixtures, настоящий stdio/HTTP MCP и
offline-discovery встроенного upstream. Реальные сообщения, контакты, сессии
и Telegram API в проверках не используются. Первый вход и проверку собственного аккаунта выполняет оператор.

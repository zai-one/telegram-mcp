## 1. Что просили и что сделано

Telegram 0.1.0 выделен в самостоятельный Git-проект: исходные адаптер и 12
MCP-инструментов, собственные stdio/Streamable HTTP, конфигурация, SQLite
журнал отправок/квот/аудита, tests, version/lock, wheel/sdist и документация.
HTTP использует RS256 JWT с account_id/issuer/audience/exp/sub/scopes; binding
аккаунта задаётся операторским JSON. stdio явно применяет локальные scopes.
Клиент не меняет binding и квоты. Запись выключена по умолчанию и ограничена
исходным allowlist; квоты сохраняются между процессами с общей SQLite.

Upstream chigwell/telegram-mcp закреплён на commit
`f1a2d8e00a7f127bb7702655c58fdfcee7e73a5a`, tag v3.2.0, metadata version 2.0.1.
Его Apache-2.0 license и provenance сохранены. Существующий патч платформы
применён, затем переписаны только импорты в приватный namespace. Хеши файлов
проверяются перед импортом. Пакет PyPI с именем telegram-mcp не используется.
Один процесс держит один неизменяемый набор credentials/write-mode; изменения
требуют перезапуска. Посторонние sessions/proxy/log/.env не подхватываются.

Неизвестный исход отправки остаётся pending, включая после отмены/перезапуска.
Повторный либо новый ключ не вызывает повтор для того же pending intent.
Доказанный локальный отказ квоты до factory получает failed, поэтому после
освобождения лимита возможен новый ключ. Центральный gateway сохраняет свой
исходный store protocol: этот standalone-only маркер там не генерируется.
Квоты измеряют операции upstream MCP, не отдельные внутренние MTProto RPC.

Кандидат платформы подключает wheel с SHA-256, а не копии исходников. Auth,
scopes, account assignment, pause, governor, audit, high-risk policy, ledger,
reconciliation и URLs остаются центральными. Standalone state/runtime/server
не запускаются внутри gateway. Сохраняются классы ошибок governor и audit.
Ветки не объединялись, FastMCP 4.0.0 и прежние зависимости gateway не обновлялись.

## 4. Что может сломаться

- Разные state files не разделяют квоты/ledger: процессы одной credential
  должны использовать общую приватную базу и согласованную конфигурацию.
- Неопределённый исход требует операторской сверки. Удаление базы, смена
  account_id или возврат старой версии не разрешают повторять отправку.
- Тип ToolError внутри upstream может потерять отдельную RPC-классификацию;
  это унаследованная нормализация. Mocked cooldown доказывает adapter →
  governor → audit, а не сохранение каждого кода Telegram внутри SDK.
- Upstream выполняет внутренние RPC/reconnect; проверены три конкретных
  offline сценария. Это не доказательство exactly-once для всех write tools.
- CI требует доставки точного wheel в MCP_SERVICE_ARTIFACT_DIRECTORY.
  Старые platform vendor snapshots сохранены только как migration provenance,
  не участвуют в текущем Docker/CI runtime и не являются местом разработки.
- Rollback — предыдущий gateway build с сохранением центрального ledger.
  Production и реальные клиентские данные в этой работе не проверялись.

## 6. Скептик

Агенты /root/yandex_state_skeptic и /root/mcp_layout_skeptic анализировали
присланный код без инструментов, памяти, файлов и сети. Это независимое чтение,
а не независимый запуск. Все четыре ответа приведены целиком:

**Вердикт: найден один конкретный P2. Доказуемого P1 по предоставленным фрагментам нет.** Проверка выполнена без инструментов и запусков; 35 пройденных тестов — авторское сообщение.

**P2 — локальный отказ admission навсегда блокирует заведомо неотправленное сообщение.**

Конкретная трасса:

1. Для разрешённого сообщения с хешем `H` и новым ключом `K1` создаётся outbox-запись `pending`.
2. `registry.call` вызывает `store.admit`. Например, текущий лимит writes уже исчерпан либо активны две leases.
3. Admission поднимает `ProviderAdmissionDenied` **до вызова factory**. Отправки не было.
4. Обработка `ProviderError` сохраняет `pending`; если исключение не относится к этому классу, общий путь также оставляет запись `pending`.
5. Через минуту лимит освобождается, но повтор с `K1` отвергается как pending. Повтор с новым `K2` блокируется SQL-проверкой того же pending-хеша `H`.
6. Предоставленного endpoint для разрешения этой ситуации нет.

**Последствие:** временное ограничение превращается в постоянный запрет повторить точное сообщение через публичный интерфейс. Пользователь получает требование reconciliation для операции, которую сервер достоверно не отправлял.

**Уверенность: высокая.** Трасса следует непосредственно из порядка reservation → admission и правил повторного обращения; поведение Telegram API здесь не требуется.

**Цена ошибочной правки:** перевод *всех* `ProviderError` в `failed` разрешил бы повтор после timeout или transport error и мог создать дубликат. Изменять обработку следует только для доказанного отказа до входа в factory. Терминальный `failed` позволил бы повторить запрос с новым ключом, сохранив запрет повторного использования прежнего.

Других доказуемых дефектов в показанной SQL-логике не установлено:

- Конкурентные reservation сериализованы; существующая запись сама по себе не разрешает отправку.
- Проверка изменённого payload выполняется вызывающим кодом до factory.
- Лимиты и leases разделяются между actors одной session label.
- Неизвестный исход сохраняет pending и блокирует повтор с новым ключом.

Остаётся непроверенная граница **`adapter.call_write → embedded Client → транспорт`**, включая внутренние retry/reconnect и распространение cancellation. Один вызов адаптера не доказывает отсутствие повторной фактической отправки внутри клиента. Без этого кода самостоятельную находку не заявляю.


**P2 закрыт по предоставленному коду. Новых доказуемых P1/P2 в этом изменении не найдено.**

`LocalPreDispatchDenied` создаётся только при отказе `store.admit`, до входа в factory. Поэтому перевод соответствующей reservation в `failed` опирается на достоверное отсутствие отправки. Новый ключ позволяет повторить сообщение после освобождения лимита; старый ключ остаётся использованным.

Исключения из factory не получают этот маркер. Timeout, transport error и даже `ProviderAdmissionDenied`, возникший внутри factory, сохраняют `pending` и запрет повторной отправки с новым ключом. Поведение gateway по описанному пути сохраняется.

**Уверенность высокая** для этой границы обработки исключений. Цена ошибочного расширения исправления — дубликаты после неизвестного исхода; текущая узкая маркировка такого расширения не делает.

Исправленный счётчик принят: **11 passed — авторский результат**, самостоятельно тесты не запускал. Внутренние повторы Telethon остаются предметом отдельной проверки.


**Чисто в пределах предоставленного кода: новых доказуемых P1/P2 не обнаружено.** Инструменты и независимые прогоны я не выполнял.

- **Ошибки и cooldown:** `AdapterBridge` переводит пакетную ошибку в центральную до выхода из callback → governor получает центральный `ProviderRateLimited` → `RegistryFacade` возвращает пакетный тип → registrar восстанавливает центральный safe envelope. В этой цепочке `retry_after_seconds` сохраняется; реконструкция `SafeToolError` сохраняет код для аудита.
- **Записи и идемпотентность:** проверка binding и `validate_write` предшествует резервированию; ledger остаётся центральным. Делегирование `call_write` без преждевременного преобразования ошибки позволяет governor обработать её. Неоднозначная ошибка оставляет запись `pending`; доказанного открытия повторной отправки или обхода approval здесь нет.
- **Композиция:** standalone state/runtime/server в описанный путь не включены. Вложенные обёртки восстанавливают контексты в `finally`; сохранение auth и схем подкреплено предоставленными авторскими результатами.

У mocked cooldown-теста есть точная граница: исключение из `_embedded_server` проверяет bridge → governor → внешний MCP/audit. Он **не проверяет сохранение типа ошибки через внутренний `Client.call_tool`**, где `ToolError` преобразуется в общий `ProviderError`. По предоставленному описанию эта нормализация унаследована; новой регрессией её не считаю.

**Уверенность средняя. Цена ошибочной правки высокая:** необоснованная смена `pending` на `failed` или разрешение повторной отправки после неоднозначного результата может привести к дублированию Telegram-записи. Оснований для такой правки представленное ревью не даёт.


**Новых доказуемых P1/P2 относительно локального переноса не обнаружено.** Вывод основан только на предоставленном описании и авторских receipts.

- Wheel проверяется по зафиксированному SHA до копирования и после него; пути ограничены заданными каталогами. Docker и frozen sync используют пакет, исключая прежнюю установку исходников из vendor-каталога.
- Авторские проверки чистого клона, одинакового wheel SHA и standalone stdio/HTTP подтверждают заявленную воспроизводимость пакета и запуск без `mcp_platform`.
- Замена AST-проверки на MCP `list_tools()` обоснована извлечением функций: проверяется фактическая регистрация tools с точным совпадением прежней таблицы стоимости. Саму таблицу для устранения FAIL не меняли.

**Полный gate пока не подтверждён:** завершённый результат — `617 passed / 1 failed / 8 skipped`; после исправления проверки повтор ещё выполняется. CI и image build также не проверены; необходимый каталог артефактов требует отдельного provisioning.

Уверенность средняя: независимого запуска не было. Оснований менять runtime или ослаблять проверки хешей нет; ошибочное ослабление последних снизит гарантию установки именно проверенного пакета.


**Что сделано по находкам:** P2 UPHELD, локальная quota denial после reservation
воспроизведена; LocalPreDispatchDenied ставится исключительно до входа в factory.
Только этот маркер позволяет failed; timeout/transport/cancellation оставляют
pending. Исправление в service 7b4b742 повторно принято скептиком. Gateway review
не нашёл новых P1/P2; полный gate и clean gateway clone, ещё выполнявшиеся в
момент review, затем завершились успешно, что подтверждают receipts выше.

**Вердикт: найден один конкретный P2. Доказуемого P1 по предоставленным фрагментам нет.** Проверка выполнена без инструментов и запусков; 35 пройденных тестов — авторское сообщение.

**P2 — локальный отказ admission навсегда блокирует заведомо неотправленное сообщение.**

Конкретная трасса:

1. Для разрешённого сообщения с хешем `H` и новым ключом `K1` создаётся outbox-запись `pending`.
2. `registry.call` вызывает `store.admit`. Например, текущий лимит writes уже исчерпан либо активны две leases.
3. Admission поднимает `ProviderAdmissionDenied` **до вызова factory**. Отправки не было.
4. Обработка `ProviderError` сохраняет `pending`; если исключение не относится к этому классу, общий путь также оставляет запись `pending`.
5. Через минуту лимит освобождается, но повтор с `K1` отвергается как pending. Повтор с новым `K2` блокируется SQL-проверкой того же pending-хеша `H`.
6. Предоставленного endpoint для разрешения этой ситуации нет.

**Последствие:** временное ограничение превращается в постоянный запрет повторить точное сообщение через публичный интерфейс. Пользователь получает требование reconciliation для операции, которую сервер достоверно не отправлял.

**Уверенность: высокая.** Трасса следует непосредственно из порядка reservation → admission и правил повторного обращения; поведение Telegram API здесь не требуется.

**Цена ошибочной правки:** перевод *всех* `ProviderError` в `failed` разрешил бы повтор после timeout или transport error и мог создать дубликат. Изменять обработку следует только для доказанного отказа до входа в factory. Терминальный `failed` позволил бы повторить запрос с новым ключом, сохранив запрет повторного использования прежнего.

Других доказуемых дефектов в показанной SQL-логике не установлено:

- Конкурентные reservation сериализованы; существующая запись сама по себе не разрешает отправку.
- Проверка изменённого payload выполняется вызывающим кодом до factory.
- Лимиты и leases разделяются между actors одной session label.
- Неизвестный исход сохраняет pending и блокирует повтор с новым ключом.

Остаётся непроверенная граница **`adapter.call_write → embedded Client → транспорт`**, включая внутренние retry/reconnect и распространение cancellation. Один вызов адаптера не доказывает отсутствие повторной фактической отправки внутри клиента. Без этого кода самостоятельную находку не заявляю.
